# Business Campaign Engine Implementation (Phase 5)

Implementation record. Builds on [23](23_NEURA_BUSINESS_MESSAGING_MASTER_BUILD_PLAN.md), [24](24_CANONICAL_MESSAGING_FOUNDATION.md), [25](25_MESSAGE_SENDER_IDENTITY_ARCHITECTURE.md), [27](27_BUSINESS_TEMPLATE_ENGINE_IMPLEMENTATION.md), [28](28_GENERIC_APPROVAL_CENTER_IMPLEMENTATION.md), [29](29_BUSINESS_CUSTOMERS_AUDIENCES_IMPLEMENTATION.md), [14](14_NEURA_BUSINESS_SAAS_SPECIFICATION.md). A campaign is an orchestration object, not a message -- it fixes WHO, WHAT, WHEN, and UNDER WHICH AUTHORITY/CONSENT before a single message is ever created. No external channel (WhatsApp/SMS/email/Meta) is called anywhere in this phase.

## 2. Campaign domain model

`campaigns`: `id, businessId, name, description?, category, status, templateVersionId?, audienceId?, createdBy, approvedBy?, approvedAt?, scheduledAt?, startedAt?, completedAt?, cancelledAt?, cancelledBy?, failureReason?, createdAt, updatedAt`. `category` is restricted to `MARKETING`/`UTILITY` (reusing `MESSAGE_CATEGORY`, not a new enum) -- `AUTHENTICATION` is explicitly excluded, reserved for a future dedicated OTP path per the brief's strict scope. No generic workflow engine was built; every field above has a concrete, named purpose.

## 3. Lifecycle / state machine

`DRAFT -> {SCHEDULED, RUNNING, CANCELLED}`, `SCHEDULED -> {RUNNING, CANCELLED}`, `RUNNING -> {COMPLETED, FAILED}`; `COMPLETED`/`CANCELLED`/`FAILED` are terminal. Enforced by `campaigns/lifecycle.ts`'s `LEGAL_TRANSITIONS` map (same pattern as `templates/lifecycle.ts`), plus an atomic `UPDATE ... WHERE status = $fromStatus` for every actual transition (same CAS idiom as Phase 3's `decide()`). Illegal transitions are rejected server-side unconditionally -- no frontend-supplied state is ever trusted. Cancellation is only supported pre-execution (`DRAFT`/`SCHEDULED`) -- a `RUNNING` campaign runs to `COMPLETED` or `FAILED`, it is not interruptible mid-run in this foundation (documented scope decision, Section 17 of the approved brief did not require mid-run cancellation).

**Deliberate deviation from Phase 2's shape**: campaigns have NO `SUBMITTED`/approval-pending status of their own. `campaigns.status` stays `DRAFT` for the entire authoring + approval-pending period; only `campaigns.approvedAt`/`approvedBy` (set exclusively by the Approval Center's policy callback) record that a decision happened. Folding a second "under review" state into `campaigns.status` would have duplicated state that the Approval Center already owns -- exactly the anti-pattern Phase 3 was built to eliminate.

## 4. Template binding

`campaigns.templateVersionId` is a fixed foreign key to one exact `templateVersions.id` row, set via `PATCH .../campaigns/:id` while `DRAFT`. Binding requires the version to be `APPROVED` at bind time (immediate feedback) AND is **re-checked live** at the DRAFT/SCHEDULED->RUNNING transition (never cached, never assumed still valid) -- if the bound version was archived/changed status after scheduling, the campaign transitions straight to `FAILED` with a recorded `failureReason`, it does not silently proceed or silently skip every recipient. Proven directly: creating a `v2` for the same template after a campaign is bound to `v1` leaves the campaign's `templateVersionId` unchanged (test: "campaign keeps using v1 even after v2 is created and approved"), and binding a `DRAFT`/`SUBMITTED`/`REJECTED`/`ARCHIVED` version is rejected outright (test: "rejects binding a DRAFT/SUBMITTED/REJECTED/ARCHIVED version", all four statuses exercised).

Campaigns additionally only support templates that declare variables from a small, fixed, code-governed set (`{"name"}` in this phase) -- `assertSupportedVariables` rejects binding a template that declares anything else at bind time, rather than discovering an unsupported variable mid-execution.

## 5. Audience / recipient snapshot strategy

**Immutable execution snapshot (option B), not live membership** -- chosen deliberately per the brief's own preference for "a serious campaign system." `campaignRecipients` is populated exactly once, at the FIRST DRAFT->SCHEDULED or DRAFT->RUNNING transition (`snapshotRecipientsIfNeeded`), by resolving `audienceMembers` for the bound `audienceId` **entirely server-side** -- the client never supplies a recipient id anywhere in the API surface. Ownership is re-verified defensively at snapshot time (every `customerId` from the membership rows is cross-checked against `customers.businessId = campaign.businessId`; a row that fails this check is silently excluded, never trusted) -- tested directly by deliberately corrupting the fake DB with a cross-business membership row and confirming it never enters the snapshot. Adding a member to the audience AFTER scheduling does not retroactively join the campaign (tested directly). A hard cap (`MAX_RECIPIENTS_PER_CAMPAIGN = 5000`) is enforced when binding an audience, so no campaign can be scheduled against an unbounded recipient set.

## 6. Recipient safety gate chain (P0)

Implemented as the exact ordered chain from the brief, in `campaigns/service.ts`'s `processOneRecipient`: business ownership (implicit in every query) -> customer exists & belongs to this business -> customer status != `BLOCKED` -> customer status != `ARCHIVED` -> `isEligibleForChannel(businessId, customerId, campaign.category)` (Phase 4's consent gate, reused verbatim -- `campaign.category` is either `marketing` or `utility`, which are literally `CUSTOMER_CONSENT_CHANNEL` values, so no translation layer was needed) -> template still `APPROVED` (checked once per campaign before the batch, not per-recipient, since it's a campaign-level fact -- see Section 4) -> render success -> billing charge succeeds -> message/delivery/event created. **Audience membership alone is never sufficient** -- proven directly by a test that blocks a customer after they're already snapshotted as a target and confirms they remain "targeted" but are never "sent" (this is the exact requirement flagged during Phase 4 hardening, doc 29 section H3, now enforced and tested here).

## 7. Consent gate

No new consent table, no Marketing Consent Engine. `isEligibleForChannel` from Phase 4 is called unmodified. Absence of a consent row is never interpreted as consent (tested: "ACTIVE + no consent -> skipped"); an explicit revoke is honored and never silently overridden by a later campaign (tested: "ACTIVE + revoked consent -> skipped").

## 8. BLOCKED/ARCHIVED gate

Both checked as independent, unconditional gates ahead of consent -- a `BLOCKED` customer is skipped (`customer_blocked`) even if they have granted marketing consent; an `ARCHIVED` customer is skipped (`customer_archived`) the same way. All six scenarios from the brief's Section 8 are tested directly and pass: `ACTIVE+eligible->sent`, `BLOCKED+eligible->NOT eligible`, `ARCHIVED+eligible->NOT eligible`, `ACTIVE+no consent->NOT eligible`, `ACTIVE+revoked consent->NOT eligible`, cross-business customer via a corrupted membership row `->NOT targeted at all` (filtered at snapshot time, stronger than "not eligible").

## 9. Billing gate

`campaigns/billing.ts`'s `chargeCampaignMessage` is a small, new, additive function -- **not** a rebuild of `billing-engine.ts` (which is entirely call/session-shaped: hold-then-flush over a live metered duration, its own reservation/ledger tables keyed by `callId`). A campaign send is instantaneous, so this is a single atomic conditional `UPDATE billing_accounts SET wallet_balance_paise = wallet_balance_paise - cost WHERE id = ? AND wallet_balance_paise >= cost`, the same fails-closed CAS idiom used everywhere else in this codebase -- proven by a dedicated test file (`campaigns-billing.test.ts`) that evaluates the real SQL expression against a fake DB, not a mocked outcome. **`PLACEHOLDER_COST_PER_MESSAGE_PAISE = 10` is explicitly NOT an approved price** -- the file header states this in writing; it exists only so the gate has a real, testable accounting effect. Credits are never charged merely because a campaign was created or scheduled -- only at the moment a message is actually about to be created, inside the same transaction as that creation and the recipient's status flip, so a charge and its send are atomically coupled (Section 10). Insufficient credit and "no billing account configured at all" are both distinct, non-crashing skip reasons, never a system error.

## 10. Idempotency

Two independent, composed mechanisms: (1) `campaignRecipients`' unique `(campaignId, customerId)` index makes the snapshot itself impossible to duplicate-target; (2) each recipient's processing happens in its own transaction that does the work (render, charge, message/delivery/event insert) and THEN attempts an atomic `UPDATE campaign_recipients SET status='sent' WHERE id=? AND status='pending'` as the LAST step -- if that final CAS affects zero rows (another process already claimed this recipient), the function throws, which rolls back the ENTIRE transaction including the charge and the message that were tentatively created, leaving no trace of a duplicate. This was not merely reasoned about -- it is directly tested with genuine `Promise.allSettled` concurrent `executeCampaign` calls against the same campaign, confirming exactly one charge and one sent message, never two (test: "concurrent execute() calls for the same campaign do not double-charge or double-send").

## 11. Scheduling

No distributed scheduler was built. `campaigns/scheduler.ts` follows the codebase's one existing convention (`setInterval`-based `start<X>Scheduler()`, mirroring `billing-scheduler.ts` and the webhook retry sweep) -- a 1-minute tick that queries `SCHEDULED` campaigns whose `scheduledAt <= now()` and calls `executeCampaign` for each. Duplicate-scheduler-execution safety is NOT achieved by making the scheduler careful (it isn't -- it's a plain loop with no locking) but by `executeCampaign` itself being safe to call redundantly/concurrently by construction (Section 10) -- a scheduler tick racing a manual `POST .../execute` call for the same campaign is exactly the scenario the concurrency test exercises. Timestamps are stored as plain `timestamp` columns (existing codebase convention, no new timezone strategy invented). Cancellation before execution is supported (Section 3). Recurring campaigns were not implemented -- not required by the brief, and no evidence of a product need for one yet.

## 12. RBAC

Three permissions, exactly as the brief asked to evaluate: `CAMPAIGNS_VIEW`, `CAMPAIGNS_MANAGE`, `CAMPAIGNS_EXECUTE`. `MANAGE` and `EXECUTE` are deliberately separate -- a user who can edit a draft campaign does not automatically gain the authority to run it (tested both directions). No `CAMPAIGNS_APPROVE` permission was added; `CAMPAIGNS_EXECUTE` doubles as the Approval Center's `decidePermission` for the `"campaign"` resource type (Section 13) -- the authority to approve a campaign for going live and the authority to actually run it are treated as one authority in this model, avoiding a 4th permission the brief said to avoid unless clearly necessary.

## 13. Approval integration

**Required, and reused entirely from Phase 3** -- no campaign-specific approval table, no duplicated approval logic. `campaigns/approval-policy.ts` registers `resourceType: "campaign"` with `submitPermission: CAMPAIGNS_MANAGE`, `decidePermission: CAMPAIGNS_EXECUTE`, `selfApprovalForbidden: true`. `isSubmittable` requires both `templateVersionId` and `audienceId` bound (tested: not submittable until both are set). `onApproved` sets `campaigns.approvedBy`/`approvedAt` -- a denormalized fast-read of the Approval Center's own decision, not a second source of truth (the Approval Center's `approvalRequests` row remains the authoritative record). `onRejected` is a deliberate no-op on `campaigns.status` -- a rejected campaign simply stays `DRAFT`, editable and resubmittable, mirroring a rejected template version's `REJECTED -> DRAFT` path without needing a matching status value of its own (Section 3). Both self-approval-forbidden and reject-then-resubmit are tested directly.

## 14. Messaging boundary

`server/modules/messaging/service.ts` was extended, not weakened: `assertValidParticipant` gained a `CUSTOMER` case (validating against the real `customers` table, tenant-scoped by `businessId` -- Phase 0 could not validate this type at all since `customers` didn't exist yet). `createBusinessConversation` was refactored into a `tx`-accepting core (`createBusinessConversationTx`) plus a thin standalone wrapper, following the exact `DbLike`/`tx: DbLike = db` convention already established in `templates/service.ts` and `approvals/service.ts` -- this lets the campaign send path compose "find-or-create conversation" + "create message" + "charge" into ONE atomic transaction per recipient (required for Section 10's idempotency guarantee). A new `findOrCreateCustomerConversation` reuses an existing business-customer conversation across multiple campaigns/messages rather than creating a new one per send.

**The P1 sender-identity protection is not reused, it is deliberately bypassed in favor of a stricter path**: campaign-sent messages are built by a wholly separate internal function (`processOneRecipient`, no client-facing entrypoint at all) that resolves the sender as the conversation's `BUSINESS`-type participant -- never `createMessage`'s human-`authenticatedUserId` path, never a client-supplied `senderParticipantId` of any kind. `generationSource: { type: "campaign", id: campaign.id }` is written into the `messagingEvents.payload` exclusively by this server-side code (doc 25 compliance) -- there is no route, no request body field, no code path by which a client can influence either the sender or the generation source of a campaign message. Tested directly: sender participant type is always `business`; `generationSource` always matches the actual campaign id.

**Known minor limitation, documented not silently accepted**: `isEligibleForChannel`'s read happens via the plain (non-`tx`) `db` handle, not inside the surrounding recipient transaction, since Phase 4's function doesn't accept a `tx` parameter. This means the consent check isn't perfectly serializable with the same transaction that performs the charge/send -- an extremely narrow window exists where a consent revocation landing in that gap could theoretically let one message through. Not exploitable by a client (no code path lets a caller induce or time this), doesn't leak data, doesn't bypass authorization -- flagged here as a real, minor, future-improvement item (give `isEligibleForChannel` an optional `tx` param), not silently patched beyond this phase's scope.

## 15. Tenant isolation

Every service function takes `businessId` explicitly and scopes every query by it; cross-business ids return `NotFoundError`, never confirming existence to a caller from another tenant (same convention as every prior phase). Tested for: URL manipulation (campaign id from another business), body manipulation (`businessId`/`status`/`createdBy` smuggled into a `.strict()` schema, rejected 400), query manipulation (invalid status filter, 400), `templateId` manipulation (binding a template from another business, `NotFoundError`), `audienceId` manipulation (same), and `campaignId` manipulation across update/schedule/execute/cancel (all four, `NotFoundError`). The cross-business-membership-row test (Section 5/8) is the deepest isolation test in this phase -- it proves tenant isolation holds even against a hypothetically corrupted join table, not just against a well-formed malicious request.

## 16. Reporting foundation

No dashboard was built. `getCampaignReport(businessId, campaignId)` returns real, derived counts from `campaignRecipients` -- `targeted` (total snapshot size), `pending`, `sent`, `skipped`, and `skippedByReason` (a breakdown keyed by the exact `CAMPAIGN_SKIP_REASON` value). Nothing is fabricated: a scheduled-but-not-yet-executed campaign reports zero `sent` (tested directly -- "never assumes 'sent' merely because scheduled"), and every count is a live read of actual row state, not a cached/estimated figure.

## 17. Audit

Reuses `audit_logs` exclusively via `campaigns/audit.ts` (same thin-wrapper pattern as every prior phase's `<module>/audit.ts`). Actions recorded: `campaign_created`, `campaign_updated` (create/update via `AUDIT_ACTION.CREATE`/`UPDATE`), `campaign_scheduled`, `campaign_started`, `campaign_completed`, `campaign_cancelled`, `campaign_failed` (five NEW `AUDIT_ACTION` values added: `SCHEDULE`, `START`, `COMPLETE`, `CANCEL`, `FAIL`). Scheduler-triggered executions pass `actorUserId: undefined` (a system action, not a user action) -- `createAuditLog`'s `userId` field is already nullable for exactly this case. No second audit system was created.

## 18. Security review

IDOR/tenant escape (closed, Section 15), template ownership (checked at bind time via the template's own `businessId`), template approval state (checked at bind time AND re-checked live at execution, Section 4), audience ownership (checked at bind time AND every membership row re-verified at snapshot time, Section 5), customer ownership (every recipient re-scoped by `businessId` inside `processOneRecipient`), BLOCKED/ARCHIVED exclusion (Section 8, tested), missing/revoked consent exclusion (Section 7, tested), duplicate execution (Section 10, tested), concurrent execution (Section 10, tested with genuine `Promise.allSettled`), campaign state transitions (atomic CAS, illegal transitions rejected, tested), unauthorized schedule/execute (RBAC-gated, `CAMPAIGNS_EXECUTE` required and distinct from `MANAGE`, tested), sender identity injection (structurally impossible -- no client-facing function accepts a sender at all in the campaign path, Section 14), `generationSource` injection (same -- no request path reaches the field, tested), `businessId`/`templateId`/`audienceId`/`campaignId` manipulation (all tested, Section 15), insufficient credit handling (fails closed, tested in both the orchestration and the dedicated billing test), audit creation (verified via the shared audit mock across the integration suite), retry behavior (Section 10), cancellation behavior (tested, pre-execution only). **No P0/P1 was found.** One minor, non-exploitable limitation was identified and documented, not hidden (Section 14's `isEligibleForChannel` transaction-boundary note).

## 19. Migration

`migrations/0009_business_campaign_engine.sql` -- 2 new tables (`campaigns`, `campaign_recipients`), fully additive. `campaigns` REFERENCES `template_versions`, `audiences`, `organizations`, `users` (no `ON DELETE` on the template/audience FKs -- a campaign remembers its binding even if the template/audience is later archived, matching the "re-check live at execution" design rather than relying on a cascade to invalidate it). `campaign_recipients` REFERENCES `campaigns` (cascade) and `customers` (cascade) and `messaging_messages` (no cascade, nullable). No `ALTER TABLE` against any pre-existing table -- unlike Phase 4, this phase's messaging-module extension (Section 14) was a pure application-layer change (new `CUSTOMER` validation branch, refactored function boundary), not a schema change, so no canonical-messaging table needed altering. **Not applied to any database** -- same standing no-local-DB constraint as every prior phase; verified via the mock-based test suite (65 new tests) instead of real execution.

## 20. Tests

65 new tests across 4 files: `campaigns.test.ts` (39, full integration using the REAL customers/audiences/templates/approvals/messaging/campaigns services together against one shared fake DB -- proving actual end-to-end wiring, same pattern as Phase 3's `approvals.test.ts`, extended further here since Phase 5 genuinely depends on real state from four prior phases), `campaigns-billing.test.ts` (6, real SQL-arithmetic evaluation against a dedicated fake DB, not a mocked charge outcome), `campaigns-rbac.test.ts` (14). `messaging-phase0.test.ts` was also updated (net +3: one outdated test removed -- it asserted `customer` participants were categorically rejected, which stopped being true the moment this phase gave `assertValidParticipant` a real backing table for them -- and four new tests added covering the new `CUSTOMER` validation branch, including its own tenant-isolation case). All 24 numbered security-test areas from the brief are covered. Complete-suite result: **527/527**, up from 465, zero regressions to Phases 0-4.

## 21. Future external-channel integration boundary

The design deliberately keeps `NEURA Campaign -> Eligibility -> Template -> Execution` entirely free of any external-provider concept. `processOneRecipient`'s final act is creating a canonical NEURA `messagingMessages` row via the existing Phase 0 model -- nothing about `chargeCampaignMessage`, `renderTemplateContent`, `isEligibleForChannel`, or the recipient snapshot mechanism knows or cares whether that message's delivery later becomes an in-app notification (today) or gets hand off to a `Channel Adapter` for SMS/Email/WhatsApp (future). The concrete extension point: a future channel adapter would subscribe to `messagingDeliveries`/`messagingEvents` for campaign-originated messages (identifiable via `messagingEvents.payload.generationSource.type === "campaign"`, already being written today) and handle the actual outbound transmission + status callback -- entirely additive, requiring no change to anything built in this phase. No Meta/WhatsApp/MSG91/Twilio/SendGrid import or dependency exists anywhere in `campaigns/` or the touched parts of `messaging/`.
